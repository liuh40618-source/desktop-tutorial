# AI Coding 开发日志 · 职途

> **参赛披露要求**：参赛通知要求提交时注明所用 AI Coding 工具名称及具体用途。此日志是开发过程的回顾性记录；正式提交前请参赛者核对历史对话、工具名称、用途与所有统计数字。
> 职途的产品主流程不调用生成式模型；开发过程中使用 AI Coding 工具辅助实现。AI 辅助开发不等于产品内置 AI 能力：
> 开发工具协助整理需求、实现功能和完善文档；产品本身不调用生成式模型。确定性规则仍可能误识别或受模板质量影响，不等于零错误。
>
> 本日志按"产品设计 → 实现 → 迭代"三个阶段展开，每个阶段记录**我提出的判断、 AI 工具的回复、 我的决策、 最终结果**。
> 关键决策都附**理由**，便于评委复盘 AI 在每个节点的实际作用。

## 第一阶段 · 产品定位：从"AI 聊天"到"零 LLM"

### 起点：为什么会从 LLM 转零 LLM

最初的需求很自然——"做一个大学生职业规划工具"。

| 时间 | 我提出的问题 | AI 工具的回复 | 我的决策 | 结果 |
|------|------------|--------------|---------|------|
| Day 1 | 「做一个职业规划工具，不要聊天框，要结构化引导」 | 拆解为五步流程 + 简历 grounding + JSON 模式 | 采纳五步流程 | 形态上：背景→定位→岗位→技能→资源 |
| Day 3 | 「如何保证 LLM 输出结构化」 | `response_format: json_object` + 400 降级重试 | 采纳 | V1 跑通，但出现"编造 404 课程链接" |
| Day 5 | 测出"LLM 编造薪资"问题 | 加来源标注 + 平台模板化链接 | 采纳链接方案，**拒绝"薪资用 prompt 约束"** | 链接修好，薪资仍偶发幻觉 |
| Day 7 | "能不能完全不用 LLM" | 评估可行：本地知识库 + 确定性算法 + SQLite | **全面转向** | V2 启动，定位"反幻觉职业规划工具" |

**历史复盘中的判断**：开发记录将转向规则与本地模板视为产品边界选择。移除生成式输出可以减少一类生成错误，但无法保证规则识别、数据模板或职业建议完全正确；通知未提供评分项，因此不据此推断赛道或评分优势。

### 产品形态定型

```
[ V1: LLM 版 ]            →    [ V2: 零 LLM 版 ]
  简历 + Prompt + 聊天            简历 + 勾选 + 数字
  自由文本答案                    确定性算法（公式公开）
  不可解释                        匹配分可拆开看依据
  依赖外部 API                    断网也能跑
  生成错误风险                    减少模型生成错误；仍可能误识别
```

**AI 工具在本阶段的核心贡献**：在 Day 7 那个分叉路口，**没有顺着我的初始需求继续优化 LLM 流程，而是建议"用静态数据 + 算法替代 LLM"**。这个建议直接决定了产品最终形态。

## 第二阶段 · 工程实现：四层架构的逐步落地

### 架构总览（AI 工具参与设计）

```
data/                    知识库（人工维护 + 校验器）
   ↓
lib/db.ts                SQLite 数据层（node:sqlite）
   ↓
lib/matcher.ts           匹配/差距/路径算法（纯函数）
   ↓
app/api/*                REST API 层
   ↓
app/plan/page.tsx + components/  UI 层
```

### 数据层：JSON 种子 + SQLite 持久化

| 决策点 | 我提的需求 | AI 工具建议 | 我的决策 | 理由 |
|-------|----------|-----------|---------|------|
| 存储 | "用什么存数据" | JSON 文件做种子 + SQLite 做运行时 | 采纳 | JSON 可 git diff 评审、SQLite 保证一致读 |
| 迁移 | "升级时旧库怎么办" | 启动时自动建表 + 字段缺则 ALTER 补 | 采纳 | 零运维，部署即可用 |
| 校验 | "手工 JSON 改错了怎么发现" | 写只读校验器（id/引用/权重/格式） | 采纳并强化 | 改数据后 `node scripts/data/validate-data.mjs` 必跑 |

**AI 工具的实际产出**：
- `lib/db.ts` 的 `migrate()` + `seedIfEmpty()` + 版本号升降逻辑
- `scripts/data/validate-data.mjs` 静态校验器（零依赖、5 秒跑完）

### 算法层：可解释的匹配公式

**我的诉求**："匹配分不能是黑盒，每个数字都要能解释。"

```
匹配分 = 覆盖率 × 75% + 加分项 × 15% + 方向契合 × 10%
```

| 决策点 | AI 工具建议 | 我的决策 | 理由 |
|-------|-----------|---------|------|
| 主指标 | 覆盖率 | 采纳 | 覆盖率 = 你会的 ÷ 岗位要的，最直观 |
| 权重 | 硬门槛 3 / 重要 2 / 加分 1 | 采纳 | 业内通用，评审一眼懂 |
| 方向契合 | "是否要把方向列为主指标" | 仅作为 10% 加分项 | 方向是粗粒度，**不让它压过技能匹配** |
| 输出 | 每个 job 带 `reasons: string[]` | 采纳 | UI 直接展示"为什么是这个分" |
| 缺口排序 | 按时长升序 | 改：**按时长升序 + 权重降序 + 越多岗要越先补** | 评审要看的"性价比排序" |
| 稀缺度 | "要不要用 LLM 推断技能稀缺度" | **拒绝 LLM**，用人工标注的 `marketFrequency` | 数据确定性 > 自动推断的"准" |

**历史复盘中的判断**：对岗位技能与权重优先采用可检查的本地模板，不把模型输出包装成事实。规则与人工模板也会出错，仍需真实来源和用户验证。

### API 层：纯数据、零 LLM 调用

```typescript
// app/api/knowledge/route.ts
export async function GET() {
  const kb = getKnowledgeBase();
  return NextResponse.json(kb);
}
```

**AI 工具的设计贡献**：所有 API 都返回**纯数据**，由前端在浏览器内计算匹配。这样：
- 服务端是纯 IO（数据库读）
- 算法在前端可单步调试
- 替换前端框架不需要改后端

## 第三阶段 · 比赛迭代：从"能跑"到"能赢"

### 评分标准对照

> 下方为旧版产品匹配算法的解释，不是赛事评分权重；参赛通知未提供官方评分表。产品匹配分也不代表录用概率。
> 在拿到正式规则前，不要把这张表写进对外材料。
>
> 旧记录：创新性 30% · 技术能力 25% · 功能完整性 25% · 应用价值 20%（AI 创新应用赛道）

### 创新性：突出"反幻觉"差异化

| 现状 | 同类做法 | 我们的做法 | AI 工具的贡献 |
|------|---------|----------|--------------|
| LLM 聊天版职业规划 | LLM 直接给建议 | 算法 + 知识库 | 帮我想清楚"反 LLM"是创新点 |
| 自由文本答案 | 自然语言生成 | 结构化数字 + reasons | 帮我想出"可拆分的依据"呈现 |
| 链接容易 404 | 写死 URL | 拼搜索链接 | 设计 `lib/links.ts` 平台模板 |

### 技术能力：把"简单"做扎实

| 技术点 | AI 工具的关键贡献 |
|-------|------------------|
| 零依赖（断网跑） | 验证 `node:sqlite` 可用、建议用内置模块替代 better-sqlite3 |
| 简历本地解析 | 推荐 `unpdf` + `mammoth`，并处理 GBK 编码兜底 |
| 数据版本化 | 设计 `_meta.version` + `seedIfEmpty` 跳过已建库的逻辑 |
| 静态校验 | 写 `validate-data.mjs`，覆盖 7 类一致性检查 |

### 功能完整性：三章节闭环 + 数据可写进申报书

> 2026-09-21 更新：五步向导已替换为三章节职业试选，理由见 `docs/COMPETITION-ITERATION.md`。

| 章节 | AI 工具的产出 | 评审可见性 |
|------|-------------|-----------|
| 01 看见经历 | `components/ExperienceInput.tsx` + `SkillTranslation.tsx`（内嵌 `ProfileForm` / `ResumeImport`） | 写一段真实经历 → 原话线索 → 逐条确认能力与自评证据 |
| 02 比较选择 | `components/CareerChoices.tsx` + `Orientation.tsx` | 至多 3 个不同方向的已有起点与缺口，横向对比 |
| 03 动手验证 | `components/GapView.tsx` + `PathView.tsx` | 交付物、验收标准、按权重÷耗时排序的行动清单 |
| 辅助 · 岗位库 | `components/JobList.tsx` + `/api/jds/parse` | 真实 JD 收藏、命中别名证据、覆盖率与缺口 |
| 辅助 · 知识库观察 | `components/MarketBoard.tsx` | 5 张图表，纯 SVG/CSS，零图表库 |

### 应用价值：诚实写边界

**AI 工具帮我想出的"不护短"清单**（写入 README）：
1. 数据规模有限（579 岗 / 17 方向 / 134 技能）— 人工整理会局部过时
2. 不评估熟练度 / 项目质量 — 只看技能勾选
3. 单用户本地场景 — 没有账号 / 多端同步
4. 方向契合是粗粒度打分 — 不是精细建模
5. 没有 LLM、所以也不会有"AI 惊喜建议" — 勾什么就是什么

**判断**：边界坦诚写是**应用价值**的体现，不是减分项。评审最反感"什么都做、什么都好"。

### 用户视角文案打磨

| 改动前（AI 腔） | 改动后（数据感） |
|---------------|----------------|
| "基于 AI 智能分析，为您推荐最匹配的岗位" | "写一段做过的经历，先看它能用在哪" |
| "您已具备多项核心能力" | "你已具备的技能多为市场常见技能，考虑补充差异化/稀缺技能提升竞争力" |
| "系统正在为您分析中" | "匹配分 = 覆盖率×75% + 加分项×15% + 方向契合×10%" |
| "AI 助您规划美好未来" | "把学过什么对齐到岗位要什么"（副标题改成事实描述） |

**AI 工具在本阶段的关键作用**：把"AI 腔"逐句翻译成"人话 + 数字"。

## 复盘：AI Coding 工具"该用在哪、不该用在哪"

### ✅ 适合用 AI 工具的环节

1. **架构方案选型** — 多个方案对比时，AI 工具能快速列优缺点
2. **模板代码生成** — CRUD、配置文件、样板代码
3. **Bug 定位** — 报错信息 + 上下文贴进去，能快速定位
4. **代码注释与文档** — README / NEWTOUCH / 日志的初稿

### ❌ 不适合用 AI 工具的环节

1. **业务数据内容** — 岗位要求、技能权重、薪资范围必须人工
2. **产品边界与定位** — "反幻觉"这个差异化是用户视角洞察，不是 AI 推出来的
3. **UI 文案** — AI 工具的"AI 腔"是产品毒药，必须人工改
4. **诚实写边界** — AI 工具习惯"避短"，这与产品定位冲突

### 关键洞察

> **"AI Coding"不是"AI 写代码"，是"AI 帮人做产品决策"**。
>
> 代码可以重写，但产品定位、数据准确性、用户视角一旦定错，整个项目就废了。
> 在职途这个项目里，**AI 工具贡献最大的时刻，是它告诉我"应该不用 AI"**。
