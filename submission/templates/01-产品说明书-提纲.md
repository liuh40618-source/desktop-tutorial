## 一、产品介绍

> 要回答：解决什么问题、给谁用、核心功能是什么。避免形容词堆砌，用可验证的表述。

建议小节：

1. **目标用户**：面向教育场景中的大学生 / 应届生，尤其是"方向不清、经历难转化为能力证据"的人群。
2. **待解决问题**：① 做过的事说不清能用在哪些岗位；② 目标方向与可执行实践脱节。
3. **产品形态**：可解释的职业技能匹配工具。三个章节——看见经历 / 比较选择 / 动手验证。
4. **核心功能**
   - 从一段真实经历出发，识别候选能力并由用户逐条确认
   - 从知识库中给出至多 3 个**不同方向**的候选，并列展示已有起点与缺口
   - 将差距转为一项有交付物与验收标准的行动，完成后记录作品与复盘
   - 支持真实 JD 粘贴识别、简历文本导入、规划导出 Markdown
5. **一句话定位**：从"我说我会"到"我能展示"。

## 二、设计思路

> 要回答：为什么这样设计，替代方案是什么，取舍依据是什么。

建议小节：

1. **关键设计决策：不做"问 AI 我适合干什么"的聊天框。**
   替代方案是 LLM 直接生成建议，被否决，理由：输出不可解释、存在幻觉、无法复核。
2. **可解释优先。** 匹配分 = 覆盖率 × 75% + 加分项 × 15% + 方向契合 × 10%，
   每个岗位结果附 `reasons` 字符串，每个数字可拆开看。
3. **用户确认优先于自动判定。** 关键词识别只作候选提示，能力与证据等级由用户确认；
   否定、学习中、经验有限等邻近表述不自动勾选。
4. **数据可控优先于覆盖面。** 岗位与技能为本地模板 + 结构校验，拒绝用模型推断
   稀缺度、薪资等不可复核的数字。
5. **边界诚实。** 明确写出"不评估熟练度""方向契合是粗粒度打分"等已知限制。

## 三、设计过程

> 要回答：从需求到成品的推进路径与关键节点。建议配时间线或架构图。

建议小节：

1. **阶段一 · 需求与形态试错**：V1 采用 LLM 生成，暴露编造链接与薪资的问题。
2. **阶段二 · 架构转向**：确立"知识库 + 算法层 + API 层 + UI 层"四层结构，
   主流程改为确定性规则，可离线运行。
3. **阶段三 · 主流程重构**：从五步向导收敛为三章节（看见经历 / 比较选择 / 动手验证）。
4. **阶段四 · 可靠性与边界**：访客会话隔离、保存失败不虚报成功、示例不覆盖个人草稿。
5. **当前状态与下一步**：待补用户验证数据、真实 JD 采样记录与工作样本审阅。

可复用的素材：`docs/COMPETITION-ITERATION.md`、`README.md` 的目录与算法章节。

## 四、商业价值与产品创新性说明

> 二选一或都写。这一节是评审区分"作业"与"产品"的地方，建议用可核验的证据，不要写未发生的成绩。

### 4.1 创新性

| 维度 | 常见做法 | 本项目做法 |
| --- | --- | --- |
| 结果形态 | LLM 生成一段建议 | 结构化分数 + 可展开的分项构成 |
| 可解释性 | 黑盒 | 公式公开，每个分数附 `reasons` |
| 数据来源 | 模型生成 | 本地模板 + 结构校验器 |
| 输出稳定性 | 依赖外部 API | 断网可运行，结果确定 |
| 交互重点 | 给答案 | 给候选 + 要求用户确认 |

### 4.2 商业价值

- **需求侧**：高校就业指导与生涯教育是持续投入场景。
- **供给侧的差异化**：现有产品多为测评问卷或聊天式咨询，缺少"可解释 + 可执行行动"的闭环。
- **可验证的落地形态**：高校就业中心试点、生涯课程配套工具、个人求职作品集工具。
- **诚实边界**：商业模式尚未经市场验证；用户效果数据仍在收集，**不要写成已验证结论**。

> 若填写本节时没有真实数据，就写清楚"尚未验证"，并给出验证计划。这比编造指标安全得多。
